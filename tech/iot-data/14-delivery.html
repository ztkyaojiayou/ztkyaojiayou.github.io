推送投递——地址、渠道与不重复

IoT 高并发实时数据链路 · 第 14 篇

投递是整个链路里唯一不可撤销的动作：消息到了人手机上，你没法把它收回来。而第三方网关大多没有幂等键。

所以这里选 at-most-once。它的可靠性不来自重试，而来自 outbox 与台账——保证「发了什么」永远可查，而不是保证「一定送到」。

说明：本文涉及的系统与规模做过脱敏处理，数字用于说明方法与量级关系，不一一对应某个具体项目。

一、搬运行：从任务到「真的送出去了」

上一篇的决议输出的是数据：发给谁、发什么。这一篇把它变成动作。

看起来只是"调个接口"，但这一层要处理五件事，每一件都独立于业务语义：

环节要解决的问题
地址这个人的手机号/邮箱/token 是什么，从哪来，过期了怎么办
渠道走短信还是电话还是邮件；一个渠道慢了会不会拖垮其它渠道
限流同一个人同一渠道，一小时内最多几条
投递调哪个网关、超时多久、失败了算成功还是失败
回执网关说"已提交"之后，到底送达了没有

这五件事都不是业务语义，所以它们被放在决议之后。这也是「决议输出纯数据、投递才碰外部世界」这个分界的价值：投递层的所有失败，都不会污染判定与决议。

二、地址：绑定表与「人换号了」

投递的第一个前提是知道往哪送。这件事比想象中麻烦，因为地址会变：手机号会换、公司邮箱随岗位变、App 的推送 token 在卸载重装之后就失效了。

这些问题有一个共同的处理原则：地址必须是一个可以失效的引用，而不是一个内嵌的字符串。也就是说，告警记录里存"发给了谁"（用户标识），而不是"发到了 138xxxx"——后者一旦号码变了，历史记录就永久错了。

当前有效地址从一份专门的绑定表里取，它有自己的生命周期：

地址类型失效信号处置
短信 / 电话网关返回空号、停机标记不可用并告警到人，不反复重试
邮件硬退信（地址不存在）同上；软退信（满箱）可重试
设备推送 token网关明确返回 token 失效从绑定表移除，等客户端重新注册

注意表格最后一列的共性：「地址失效」不是投递失败，而是数据问题。把它当投递失败去重试，只会把网关打出一堆必然失败的请求；正确做法是反馈给绑定表，让下一次决议就知道"这个人这个渠道已经不可用了"。

三、渠道分池：一个慢了不能拖住其它

第二个前提是隔离。短信、邮件、电话外呼是三个完全不同的外部依赖，延迟特征差得很远——短信可能几十毫秒就返回，而电话外呼要等人接、可能几十秒。

如果它们共用同一个线程池，会立刻出现一个熟悉的问题：电话外呼把线程占满了，短信全堵在后面。于是"某个渠道慢"变成了"所有渠道都慢"。

所以投递侧按渠道分池，每个池有自己的并发上限与队列：

渠道隔离的目标不是「让每个渠道更快」，而是让慢的那个只影响自己。

分池之后还能做一件更细的事：按渠道单独降级。短信网关挂了，可以只停短信，邮件和电话照常——这个决定不需要动决议逻辑，只需要拨投递侧的渠道开关。这是"决议与投递分离"的第二个好处。

四、限流：保护的是接收方，不只是成本

第三个前提是限流，而它经常被误解为"省钱"。其实它保护的首要是接收方——一个人一小时收到五十条告警，他会关掉通知，然后彻底失联。

限流的维度选得很关键。我们用的是「人 × 渠道」的桶：

维度选法问题
按告警类型限同一个人的噪声总量仍然不受控——三种类型各发十条，他还是收到三十条
按全局限会把某个人的额度消耗在别人身上，完全失去公平性
按「人 × 渠道」✅ 直接对应"一个人被某个渠道打扰的次数"，也能按渠道单独调

这里有一个很容易漏的细节：升级链上的每一步也必须计同一个桶。如果首发渠道和升级渠道各算一份配额，那一条长度为 3 的升级链就会烧掉 3 倍额度——而额度本来是保护接收方的，这一漏等于保护形同虚设。

还有三点值得写清楚：

  • 计数必须在共享存储里。限流状态放进程内，多副本就等于把配额乘以副本数——和第 4 篇里 MQTT 的多副本问题是同一类错误。
  • 被限流不等于被丢弃。它应该被记成一个明确的理由码（"本小时额度已满"），而不是静默消失。否则用户投诉"没收到"时，你既证明不了发了、也证明不了没发。
  • 限流的失败方向要选。共享存储不可用时，是放行还是拒绝？放行会打爆接收方，拒绝会丢告警。我们的选择是放行 + 计数告警——因为限流是"少打扰"的优化，不该在故障时变成"漏告警"的原因。

最后一条和上一篇的降级方向是一致的：任何保护性机制在自身故障时，都应该退回到"不保护"而不是"阻断业务"。

把上一篇的三种手段和这里的限流放在一起，可以看清它们各自管什么：

手段减少的是例子
去重同一件事的重复同一条告警重投三次，只提醒一次
聚合同一类事的多条十台设备同一故障，合成一条
限流总量，不管是不是同一件事这个人这个渠道，一小时最多 20 条

三者的顺序也重要：去重和聚合在决议里做，限流在投递前做。因为前两者需要业务语义（什么算"同一件事"），而限流只需要计数——把它放进决议，会让那个纯函数开始依赖一个高频变化的计数器。

五、at-most-once：为什么这里必须「宁可少发」

到了这一节，是整篇最核心的取舍。

前面所有环节都可以 at-least-once：历史写错了可以覆盖、实时快照重投无害、告警事件有唯一键。但投递不行，原因很直接：

第三方渠道没有幂等键——你没法对运营商说「刚才那条别重复发」。

于是重试的代价是真实的：用户手机上真的会多一条。深夜两条重复的电话，比漏一条更能消耗人对系统的信任。

语义重复的后果遗漏的后果适用
at-least-once用户收到两条无历史、快照、事件
at-most-once无收不到，但账上有记录投递

关键在于右边那句"账上有记录"：at-most-once 不是"放弃可靠性"，而是把可靠性从"保证送达"换成了"保证可查"。漏了能被发现、能被人工补发——这比"重复轰炸用户"好得多。

六、outbox：决议与投递之间为什么要隔一张表

到这里有个问题：既然决议是纯函数、投递要碰外部世界，那为什么不干脆"决议完直接调渠道"？

因为中间没有任何载体。决议在内存里跑完，进程一挂，这次决定就消失了——没有记录说明"这条告警本该发给谁"，也就没有任何办法补。所以两者之间必须隔一层可靠的任务表，这就是 outbox 的思想。

不过 outbox 有严格与宽松两种落地方式，差别很大：

形态做法保证代价
严格 outbox 业务状态变更与写 outbox 行放在同一个本地事务里；再由 relay 扫表发布 业务动作与消息原子：要么都成，要么都不成 要额外一套 relay；要处理"发布成功但标记失败"导致的重复发布
台账 + 扫描 任务落表，由消费方推进状态；卡住的由定时扫描捞起 任务不丢、可推进 推进有延迟；多副本谁来扫要先定

我们用的是后者的变体：任务先落表，投递侧推进状态，卡在中间态的由几条定时扫描捞起来继续推进（重试、聚合冲刷、升级各一条）。

选宽松形态的理由很实在：通知这件事本来就不需要"业务与消息原子"。决议的产物是"要通知谁"，即便某次多产出一条重复任务，投递侧的幂等键也会把它挡住；反过来，为了原子性引入 relay 与重复发布处理，复杂度不成比例。

但宽松形态有两个必须回答的问题：

  • 谁来扫？多副本下如果每台都扫，就会重复推进同一个任务。要么用租约让同一时刻只有一台在扫，要么让扫描本身依赖幂等（扫到了先抢、抢不到就走）。散弹式的"大家一起扫"是最容易埋雷的写法。
  • 扫的粒度？全表扫是灾难。必须按「状态 + 时间」建索引，只捞那些"卡在中间态且超过 N 分钟"的行，而且要有条数上限——扫描任务自己也需要背压。

这就是为什么第六节和第七节要连着看：outbox 回答"为什么隔一张表"，台账回答"这张表长什么样"。

七、台账：投递的唯一事实来源

台账是这一层的核心，它要同时满足三个要求：唯一、可推进、可回查。

① 唯一：每条投递任务只有一行

决议可能因为重试而重复产出同一个任务，所以任务要有幂等键——最自然的是「告警 id + 接收人 + 渠道」。有了唯一索引，重复产出只会撞键，不会变成两条投递。

这一步是多副本安全的基础：两台机器同时处理同一个任务，只有一台能成功插入，另一台直接放弃。

顺便澄清一个常见混淆：投递台账不是告警记录。台账回答的是"这条通知发给了谁、发到哪一步了"，它的生命周期跟着一次投递；而告警记录回答的是"这个故障什么时候发生、什么时候恢复"，它是业务事实，要长期保留、可审计。两者是两张表、两套保留策略，混成一张的后果是——要么台账把告警表撑爆，要么告警的审计字段被投递细节污染。

② 可推进：状态机而不是「成功 / 失败」

投递不是二元的成功或失败，它中间有几个明确的状态，把它们记下来比记一个布尔值有用得多：

第三个状态尤其重要：「已提交渠道」不等于「已送达」。网关受理只代表它接了这个请求，真正到达用户手机是另一回事。把这两个状态分开记，才能在用户说"我没收到"时，准确说出是"我们没发"还是"发了但没到"。

③ 可回查：失败要带原因，而不是一个 false

失败的原因决定了处置方式，所以台账里必须存原因码：

  • 地址不可用（空号、token 失效）→ 反馈到绑定表，人工确认；
  • 渠道限流 → 可以延后补发；
  • 内容被拒（模板不匹配、长度超限）→ 是配置问题，必须报警；
  • 超时未知 → 最麻烦：不知道对方收没收到。按 at-most-once 不重试，标记为"待人工确认"。

最后一条是这个设计里最难、也最诚实的一处：有些情况就是不可知的。诚实地记成"未知"，比猜一个"成功"或"失败"都有用。

八、回执与对账

投递之后，回执会以异步方式回来，而且不一定每条都回来——不同渠道的回执质量差别很大，有的几乎总能回来，有的一直不齐。

所以对账是必需的，而它只问一个问题：提交了的，回来没有？

情形含义处置
提交了、回执成功确实送达正常，归档
提交了、回执失败确实没送达按原因码处置（地址 / 内容 / 限流）
提交了、回执没来未知超时后标记待确认，计入缺口指标，不自动重试

第三行的数量本身就是个很重要的指标：「提交了但没有回执」的条数。它长期为零说明对账跑通；它突然上涨说明渠道侧的回执接口出了问题——而此时投递看起来一切正常，因为该发的都发出去了。

这正是这篇的一个伏笔：投递链路的健康度，不能只看"成功率"。成功率的分母是"提交了多少"，而真正该盯的是「发出了多少」与「确认送达了多少」之间的差。

具体来说，这条链上有四个数值得常驻在看板上：

指标它回答什么异常时的含义
提交量 − 回执量有多少条下落不明渠道侧的回执接口出问题了
限流拒绝量有多少人这个小时被压住要么真有风暴，要么额度配得太紧
地址失效量有多少绑定已经过期人事/权限数据没同步，需要清理
卡在中间态的任务数扫描器有没有在干活扫描停了，或者租约卡住了

这四个数有一个共同的特性：它们都不在"成功/失败"这个维度上。成功率高不代表没有缺口，失败率高也不一定代表用户没收到——真正解释问题的是"量差"，而不是"比率"。

九、边界：什么时候不用这么较真

  • 只有站内渠道。通知只推给页面和内部 IM，没有第三方网关，重复的代价很低，at-least-once 反而更简单。
  • 不承担时效责任。比如每日汇总，晚半小时、偶尔丢一天都无所谓，台账与回执对账都可以简化。
  • 渠道本身提供幂等键。少数企业级网关支持去重键，此时可以放心用 at-least-once。
  • 量极小。一天几十条通知，人工核对都比建台账便宜——但要写下这个前提，它通常会在业务规模化后失效。
