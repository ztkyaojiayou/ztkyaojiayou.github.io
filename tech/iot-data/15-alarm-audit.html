告警审计存储——分区、归档与时间锚幂等键

IoT 高并发实时数据链路 · 第 15 篇

分区要求「按时间切」，幂等要求「全局唯一」，而 PostgreSQL 的唯一索引必须包含分区键——这两件事在字面上是冲突的。

解法不是放弃其中一个，而是给幂等键加时间锚：让「分区内唯一」自动等价于「业务唯一」。约束不可动，就改编码。

说明：本文涉及的系统与规模做过脱敏处理，数字用于说明方法与量级关系，不一一对应某个具体项目。

一、先把三种记录分清

告警这条链上至少有三张表，它们长得像，性质完全不同。混在一起讨论，问题会越说越乱：

表记什么会不会改回答的问题
告警记录 一条告警的当前状态：活跃 / 已确认 / 已恢复 ✅ 会被 UPDATE 「这个故障现在怎么样了」
审计流水 事件：raised / acked / recovered / escalated ❌ 纯追加，永不修改 「历史上到底发生过什么」
通知台账 每条通知发给了谁、投递到哪一步 ✅ 状态推进 「这条消息送出去了没」

混成一张的后果是双向的：状态机被流水淹没（一条告警确认三次就有三行，想查"现在"得自己算最新态），或者流水被更新的行覆盖（历史被改写，审计失去意义）。

这一篇只讲第二张：审计流水。

二、审计流水为什么必须是纯追加

先回答一个前置问题：既然告警记录里已经有状态了，为什么还要单独存一份流水？

因为两者回答的问题不同。状态记录回答"现在怎么样"，但它答不了"三个月前那次越限，是谁在几点确认的、当时有没有升级过、中间有没有被抑制过"。这类问题只有流水能回答——它记的不是结果，是过程。

而"过程"要能当证据用，就必须满足一条铁律：

流水只能追加，不能修改，也不能删除（在保留期内）。
改一行，就等于篡改历史。

这条铁律反过来带来一个好处：它的写入极其简单。没有更新、没有随机寻道、没有并发写同一行的冲突——只有顺序追加。在一个到处是状态机的系统里，这是最省心的那张表。

审计流水的保留期也不由业务决定，而由合规要求决定：出了事故要能回溯多久，就留多久。这一点直接引出下一节。

顺带一个常被忽略的细节："不能删"和"保留期"并不矛盾。保留期内不可改不可删，是为了保证这段历史可信；保留期到了整段丢弃，是因为再留着也没有合规价值、而成本是持续的。这两件事分开定义，才不会被"反正要删"带偏成"那就随便改"。

三、按月分区：真正的好处不是查询快

时间序列类的表几乎都会分区，理由常常被说成"查询快"。但对我们这张表来说，分区最大的价值是能整段丢弃。

想想保留期到了会发生什么。如果不分区，你只能：

DELETE FROM alarm_log WHERE ts < ?

这在 PostgreSQL 里是有代价的：删除会产生大量死元组，等 autovacuum 慢慢回收——而回收期间表和索引都在膨胀，查询变慢、磁盘吃紧。一次删几千万行，可能让整个实例难受好几天。

分区之后，动作变成了：

DROP TABLE alarm_log_202601

秒级完成，不产生死元组，不触发 vacuum，磁盘空间立刻归还。同样一件事，代价差两三个数量级。

所以我们的设计是按月做范围分区，并有一个维护任务提前把未来几个月的分区建好——分区的创建必须跑在写入前面，否则跨月那一刻就会写入失败。

顺带还有两个好处：查询能按时间裁剪（只扫相关分区），以及上一节那条"保留期按合规定"变得可执行——留多久就是留几个分区。

分区维护的三条运维纪律

分区不是建一次就完事，它有一条必须有人守着的维护链：

  • 提前建。跨月那一刻如果新分区还没建，写入会直接失败。所以维护任务要提前建未来几个月的分区，并且"建分区失败"必须是一条能触发告警的指标——而不是等跨月当天才发现。
  • 控制总数。分区不是越多越好：每个分区都有自己的索引与统计信息，规划器在选择分区时也要花时间。按月分区、只留规划期内的，是合适的粒度。
  • 边界要单实例执行。多副本环境下，建分区/归档这类维护任务必须用租约保证同一时刻只有一台上——重复执行 DETACH 或 DROP 会直接报错，甚至删除不该删的东西。

它实际是被怎么查的

分区的形状要跟着查询走，所以得先知道这张表实际被怎么用。审计流水的查询几乎只有三种，而且都带时间：

查询典型形态依赖什么
某条告警的完整历史 给我这个告警 id 的全部事件，按时间排 告警 id + 时间的联合索引
某段时间内谁确认了什么 按时间范围 + 操作人 时间范围（分区裁剪）+ 操作人索引
合规回溯 某个场站某个月的纠纷，全部拉出来 时间范围 + 场站维度

三种查询有一个共同前提：时间范围一定给。这不是限制，而是设计——审计表的索引因此可以以时间为第一列，天然和分区裁剪对齐。

反过来，如果没有时间范围的查询（比如"这个设备历史上所有告警"）成了常态，说明它在被当成业务查询表用，而不是审计表——那时候该优化的不是索引，而是换一张表。

四、分区的硬约束：PostgreSQL 拿不到全局唯一

分区带来一个必须知道的限制，而它常常在出问题之后才被发现：

PostgreSQL 没有全局索引（那是 Oracle 的能力）。
所以分区表上的唯一索引，必须包含分区键。

换句话说，你没法在分区表上声明"这一列全局唯一"，只能声明"这一列在这个分区内唯一"。

这个限制立刻和审计流水的一个核心需求撞上了：同一个事件被重复消费时，不能记两行。而"不能重复"天然是一个全局诉求——你怎么保证这个事件 id 在上个月的分区里没出现过？

到这里看似走进了死胡同：要么放弃分区（失去整段丢弃的能力），要么放弃唯一性（接受重复）。

五、时间锚：把「不可兼得」换成「换个编码就兼得」

解法不是二选一，而是注意到一件事：唯一索引既然必须包含分区键，那就把分区键编进幂等键本身。

也就是说，幂等键从"事件 id"变成"事件 id + 一个时间锚"。这样"分区内唯一"就自动等价于"业务唯一"——因为同一个事件只可能落在同一个时间锚上，进而在同一个分区里被拦住。

时间锚怎么取，取决于这条流水记的是什么业态。不同业态的时间粒度不一样，锚法也就不一样：

业态时间锚取什么为什么
逐条事件 分钟桶（把时间截断到分钟） 同一分钟内同一条告警的重投，应该收敛成一条
聚合摘要 代际（按窗口宽度对齐的时间栅格） 聚合是按窗口出的，同一窗口只能有一条摘要
升级动作 承诺时刻（armed 的那一刻） 升级是"承诺—兑现"两步，同一承诺只能兑现一次

这三种锚法有一个共同点：它们都在写入方手里就有，不需要查库。这一点很重要——如果幂等键需要先查一下"这个键存不存在"才能构造，那就又回到了一次全局查询。

这个技巧的代价也要说清楚：

  • 幂等键变长，索引体积略微增加；
  • 跨边界的事件可能被记两次。如果一个事件的时间戳刚好落在分区边界附近，而重投时时间锚算了另一个桶，两次就可能进不同分区。处理方式是把锚的粒度取得比分区粒度细得多（分钟 vs 月），让这种重合几乎不可能发生；剩下极小概率的重复，靠第七节的探针发现。

但这仍是一个非常好的交易：用编码上的一点技巧，换掉了"分区"与"幂等"的正面冲突。

六、写入口径：谁在写、什么时候写、要不要进事务

谁在写、什么时候写

先明确一件事：审计流水不是由某一个服务统一写的。它记录的是"发生后的事实"，而事实产生的地方有四处，所以写入点也有四处：

事件谁写时机同步还是异步
产生（raised） 告警事件消费者 消费到一条判定事件时 异步（消息驱动）
确认（acked） 告警业务的接口层 有人点"确认"那一刻 同步（用户请求里）
恢复（recovered） 告警事件消费者 消费到恢复事件时 异步
升级（escalated） 升级扫描器 兑现"承诺"的那一刻 定时任务

四个写入点、三种触发方式（消息、请求、定时），这就带来一个必须守住的纪律：

所有写入点必须走同一个写入入口，由它统一构造幂等键与时间锚。

为什么这条这么重要？因为第五节的时间锚是有规则的——分钟桶、代际、承诺时刻，各不相同。如果某个写入点（比如确认接口）图省事自己拼了一行 SQL，忘了带时间锚，那条记录就绕过了唯一索引；而唯一索引恰恰是防重复的唯一防线。这种漏法不会报错，只会在对账探针上表现为"偶尔多一行"。

统一入口还带来第二个好处：审计字段的完整性只在一个地方保证。设备、测点、规则、级别这些上下文，只要入口函数要求必填，就不可能出现"某类事件少了字段"的情况。

要不要和状态记录进同一个事务

还有一个容易被"统一架构"带偏的问题：状态记录与审计流水，要不要写在同一个事务里？

答案取决于它们各自在哪里。

要写的东西在哪能不能原子做法
状态记录 + 审计流水 同一个库 ✅ 能 就用本地事务——一次提交，两条落定
上面的结果 + 通知任务 库 + 消息队列 ❌ 不能 outbox：先落表，再发消息

第一行经常被做错。一个很常见的思路是"为了架构统一，所有跨组件写都异步"——于是状态更新走一个事务、流水通过消息异步写。结果是：状态改了、流水没记，而审计恰恰是用来回答"当时到底发生了什么"的。

判断标准其实很简单：能放进同一个本地事务的，就不要拆成异步。拆开只在你确实需要跨系统时才划算——因为一旦拆开，你就必须额外承担"异步失败怎么办"的一整套成本（重试、去重、对账），而这些成本在同一个库的事务里本来就是零。

反过来说，也不要为了"原子"而把不该放进事务的东西塞进去。比如调第三方网关、发消息——这些一旦放进事务，事务的持有时长就取决于外部系统，一个慢网关能把数据库连接池拖死。

所以这条链上的边界是清楚的：同一个库里的事用事务；跨库跨系统的事用 outbox 与对账。前者便宜、后者昂贵，别把便宜的做成昂贵的。

七、归档：四步，顺序不可交换

分区解决了"过期怎么删"，但保留期不是"删掉就完了"——很多场景要求"过期之后还查得到，只是慢一点"。于是要归档。

归档的正确顺序是四步，而且顺序不可交换：

  1. 摘除：把分区从主表上摘下来（`DETACH`），它就不再参与正常查询，但数据还在；
  2. 导出：把这一整个分区导成文件；
  3. 压缩并上传到对象存储；
  4. 确认上传成功之后，才真正删除这个分区。

为什么不能先删再传？因为删除是不可逆的。传失败、传了一半、对象存储暂时不可用——这些都会发生，而那时数据已经没了。

这和前面几篇反复出现的是同一条原则：两个资源不能原子操作时，顺序要保证失败一侧是"可发现且可补"的那一边。这里失败一侧必须是"分区还挂在库里"，而不是"分区已经没了"。

配套还需要一张归档索引表：记下哪个分区、什么时候、存到了哪个对象、多大、校验值。没有它，一年后有人问"2026 年 1 月的数据还在不在"，你只能去翻对象存储的目录猜。

还有一个容易忽略的动作：归档任务必须产出两个数——「已成功归档的分区数」和「已到保留期但尚未归档的分区数」。后者只要不为零，就意味着有数据正处在"即将被删但还没备份"的窗口里。

八、怎么证明它真的没重复

第五节的唯一索引是"防线"，但防线是否真的生效，需要另一样东西来证明：观测。

因为重复可能来自好几条我们没法完全消除的路径：跨分区边界的时间锚偏移、维护任务期间的并发写、以及将来某个改动不小心把唯一索引去掉了。这些都是"设计上不该发生，但发生了不会报错"的情况。

所以我们用一个探针定期去问库：近 N 天里，有多少组重复（同一幂等键出现多次）、净多出多少行，并把它暴露成一个可观测的数字。

这个指标的价值在于：

  • 它长期为零 → 说明防线在生效，可以放心；
  • 它开始非零 → 说明某条路径漏了，而且你能立刻知道是从哪天开始的（因为探针是按天扫的）；
  • 它突然暴涨 → 多半是重投或重放出了规模问题，而不是偶发。

探针本身也要克制。它是一条对审计表的聚合查询，如果每天都扫全表，就成了"为了观测重复，反而制造一次全表扫描"。我们把它限制在最近几天的分区上——重复绝大多数是新近产生的，老数据重复了也无从补救；并且只在低峰期跑，结果写成一个 gauge，供看板读取。

这也是"可观测"和"成本"之间的常态取舍：观测本身要花钱，所以要选一个"覆盖最可能出问题的那一段"的窗口，而不是全量。如果要更严格的保证，做法不是在探针上加码，而是把唯一索引做扎实——防线和探针各有分工，别让探针去补防线的洞。

这也是这一篇和最后一篇（静默失败）的接口：审计表的重复不会让任何请求失败。它只是让"历史上发生过什么"这句话变得不那么可信——而这类退化，只有主动去比对才看得见——它不会让任何请求失败，也不会让任何页面报错。

九、边界：什么时候不用这么讲究

  • 数据量小、保留期短。一年只有几十万行、只留三个月，一张普通表加个索引就够了，分区只是增加维护成本。
  • 不需要长期回溯。如果合规上不要求"几年后可查"，那么过期直接删，归档这一整套都可以省掉。
  • 重复本身无害。某些场景下审计只用于统计趋势，多一行不影响结论——那就不必为唯一性引入时间锚。
  • 没有跨系统写入。如果审计行由同一个事务写入、且没有重投路径，重复的可能性本来就很低，唯一索引只是锦上添花。
