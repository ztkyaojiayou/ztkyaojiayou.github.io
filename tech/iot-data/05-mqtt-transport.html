边缘到平台的第一跳——为什么是 MQTT，不是 Kafka

IoT 高并发实时数据链路 · 第 5 篇

下游明明是 Kafka，为什么不让设备直接写 Kafka？因为Kafka 假设的那几个前提，在现场一条都不成立：稳定的链路、够用的客户端资源、可控的连接规模、内网的信任边界。

更关键的是：MQTT 的 QoS 是「逐跳的传输保证」，不是「存储保证」。理解了这句话，才知道为什么这一跳的后面必须再放一个 Kafka——不是架构洁癖，是「不存就真的没了」。

说明：本文涉及的系统与规模做过脱敏处理，数字用于说明方法与量级关系，不一一对应某个具体项目。

一、一个被问过很多次的问题

「你们边缘网关为什么不直接把数据写进 Kafka？少一跳不是更快、更简单吗？」

这个问题值得认真回答，因为它触及了两段式传输的真正理由。直觉上「中间加一个 broker」确实像多余的组件——多一跳、多一个要运维的东西、多一处可能出故障的地方。

但实际链路是这样的：

这条线不是随手画的。每一段解决的是完全不同的问题，而且边界正好落在「网络信任边界」上——左边是公网或专线上的现场，右边是平台内网。

二、不是「边缘就该 MQTT」，而是「现场就该 MQTT」

先把一个常见误解拆掉：判断标准不是「谁发的」，而是「源在哪条链路上」。

我们有一个服务就坐在机房里，从上游系统拉数据然后直接写 Kafka，一条 MQTT 都没有。它是错的吗？不是——因为它面对的是稳定内网、少量固定上游、没有弱网也没有 NAT。对这种情况，硬塞一跳 MQTT 只是多一层没有收益的转发。

所以准确的说法是：

MQTT 解决「把不靠谱的现场链路收进平台」；Kafka 解决「进平台之后的大规模扇出、顺序与回放」。
传输协议按链路位置选，不按角色选。

只有当源所在的那条链路确实不靠谱时，MQTT 才是必需品。而风机、光伏、储能这些现场，恰恰把「不靠谱」占全了。

三、四道前提，Kafka 一条都不满足

Kafka 的 producer 是为数据中心设计的。它在设计时默认了四件事，而这四件事在现场全都不成立：

Kafka 的隐含前提现场的实际情况后果
客户端资源够用（跑得动重型客户端） 边缘盒子资源有限，设备侧常年不升级 把客户端库及其依赖塞进现场设备，是一个长期的维护负担
链路稳定、时延可控 公网/专线混杂、NAT 后面、频繁闪断 producer 的重连与缓冲要靠业务自己写，等于在应用层重造一个 MQTT
信任边界在内网 现场在边界之外 Kafka 集群要暴露到现场链路，证书、ACL、端口全部外扩
主题粒度粗、顺序靠分区 天然是「租户 / 站点 / 设备」的层级，要按设备授权 topic 层级表达能力不够，ACL 得靠命名约定硬凑

其中第二条最要命。Kafka producer 的「可靠」是建立在「链路相对稳定」上的：它会把消息攒批、在内存里缓冲、失败重试。但这些机制在现场弱网下的行为，和一条带会话的长连接完全不同。与其在设备上模拟一套长连接语义，不如直接用一个为长连接设计的协议。

第三条是安全边界，经常被低估。把 Kafka 集群暴露给现场，意味着整个平台的消息总线要在公网上开一个口子；而 MQTT broker 天生就该站在边界上，只终结设备的 TLS 连接，Kafka 留在内网，现场永远够不到。

四、长连接挂在谁身上

这条链路里有个容易搞混的点：长连接不是挂在处理程序上，而是挂在 broker 上。

我们中间的 FEP（前置处理层）做点表翻译、值闸、去重、攒批，看起来像「接入网关」，但它其实是 MQTT 的订阅者——设备的长连接终结在 broker，不在 FEP。

这个解耦带来的直接好处是：扩缩 FEP，现场一条连接都不用动。FEP 扩容时新实例只是多一个订阅者；缩容时只是少一个。如果让设备直连 FEP，那每次扩缩容都会打断现场连接，而现场连接的重建是最贵、最容易出问题的一步。

顺着这条线，还能纠正一个概念错误：长连接 ≠ 有状态。

「无状态」指的是业务状态不放在本地、丢掉任意一个实例都不影响正确性，和它握着多少条 TCP 连接没关系。FEP 的连接、点表缓存都可以丢——丢了从上游重建。但它有一个真正的状态：每台设备的入站去重水位（记着「这台设备我处理到第几号了」）。

这个状态决定了 FEP 怎么扩：不能简单地轮询分发，否则同一台设备的相邻两帧进了不同实例，去重水位就对不上，重复数据会漏过去。做法是用共享订阅 + 按 topic 哈希的 sticky 分发：同一台设备的消息永远进同一个实例，同时实例之间还能分摊总负载。

这里还有个容易踩的坑：broker 的共享订阅默认是轮询的。轮询在「每台设备都有序」这件事上是错的，它会安静地破坏去重，而且不报错——只有等到某天发现重复数据变多了，才会怀疑到这里。

五、顺序是在哪一段被保证的

「同一台设备的数据要按产生顺序处理」——这个要求听起来简单，但在这条四段式的链路上，顺序不是靠某一处集中保证的，而是靠每一段都用同一个键分片。

四段各自做的事：

段怎么保证「同设备有序」
边缘 → broker同一台设备固定发同一个 topic，走的也是同一条长连接
broker → 订阅者同一条连接上的消息是有序的；共享订阅必须按 topic 哈希粘住同一实例
FEP → Kafka用设备 ID 作消息 key，同设备必然进同一分区
Kafka → 消费者分区内有序，消费组按分区分配

关键在于四段用的是同一个「有序单位」——设备。只要中间有任何一段换了个分片维度（比如按时间轮询、按消息序号取模），顺序就在那里断掉了。而断掉之后的症状非常隐蔽：数据一条不少，只是偶尔乱序，下游如果按「后到的覆盖先到的」写入，就会写错值，而且不会报任何错。

这也是为什么「共享订阅默认轮询」是个坑：轮询的分片维度不是设备，而是「轮到你」。它满足了负载均衡，却悄悄把顺序打散了。

六、最反直觉的一点：QoS1 不保证「存得住」

这一节是我认为整篇最值得记住的。

很多人的心智模型是：「MQTT 配了 QoS1，消息至少会送达一次，所以不会丢。」这个模型在「订阅方暂时跟不上」这个场景下是不成立的。要理解为什么，得看 PUBACK 是在哪一步回的：

broker 收到 PUBLISH 之后立刻回 PUBACK，不等订阅方拿到。
所以发布方永远感觉良好——他发得快不快，跟订阅方有没有在挨饿完全无关。

那消息去哪了？进 broker 内存里、每个订阅会话各自的一个有界队列。有界是关键：队列满了，超出的部分直接丢。

更细的三层事实：

  1. 队列在内存里，不落盘。MQTT 的 QoS 是「逐跳的传输保证」，不是「存储保证」。它保证的是「不因为网络丢」，不保证「broker 会替你保存」。
  2. 想让它替你排队，得开持久会话（订阅方离线期间 broker 继续排队）。但即便开了持久会话，主流的 broker 实现默认仍然不落盘——持久会话解决的是「会话不丢」，不是「消息永久保存」。
  3. 我们连持久会话都没要。FEP 用的是 clean session：断线即会话销毁，队列一起没。这是有意的取舍——换来的是 FEP 无状态、可随意扩缩容。代价是 MQTT 这一段零持久化，broker 一重启，在途消息全没。

把这三层串起来，就能回答第一节那个问题：MQTT 后面必须有一个 Kafka，不是架构洁癖，是因为这一跳真的会丢。Kafka 提供的是磁盘留存、消费位点、按需回放——这三件事恰好是 MQTT 不做的，也恰好是平台侧需要的。

换句话说，两段式的分工是：MQTT 负责「尽力接进来」，Kafka 负责「接进来之后不再丢」。前者不可能做到后者，后者也不该去做前者的活。

七、这一层要扛多少

这里必须先澄清一个很容易搞错的数：broker 上的连接数不是设备数。

设备不直接连 broker——它们连的是站端的边缘网关（Modbus、104，或者从站控系统把标准点拉过来），一个场站一台网关，网关再向上开一条 MQTT 连接。1.2 万台设备、每站 100–200 台，算下来是60–120 条连接。而报文率仍然是每台设备每周期一条，也就是 1.2 万条/秒。

报文条数跟设备走，连接数跟场站走——
这两个数在同一层上差了将近 100 倍。

分开算，这一层的两个维度都很宽裕：

要扛多少实测余量
吞吐 入站 1.2 万条/秒 × 扇出份数 同机可吞约 40–50 万条/秒，此时整机 91% 忙 三十倍以上；自身顶一直没测到
连接 60–120 条 每连接约十几 KB ⇒ 合计个位数 MB 可以忽略

所以诚实的结论是：这一层几乎不是瓶颈。它是全链路上余量最大的几个节点之一——因为真正的"海量连接"已经在边缘那一跳被网关吃掉了。

但这条结论不能推得太远。它成立的前提是「设备先聚合到网关」这个拓扑。一旦换成设备直连 broker（这是 MQTT 更常见的用法，几十万条连接），墙立刻变成连接数 × 每连接内存，而且是线性的：十个 G 的内存在几十万连接面前并不算多。所以"连接是不是瓶颈"这个问题，答案取决于拓扑，不取决于协议。

于是就有一个很实用的判断：吞吐上不去时，先怀疑订阅者，别怀疑 broker。后面两节说的两件事——订阅者被掐断、重连风暴——都发生在这个前提下：broker 本身闲着，但你收不到数据。

八、过载时，两段链路的失败方式完全不同

上面那个语义差异，在过载时表现得最直接。做过一次压测之后，我们对这两段链路的「坏法」有了完全不同的认识：

下游跟不上时上游感受数据
Kafka 数据留在盘上，消费积压（lag）涨 完全无感 留存期内一条不丢
MQTT（QoS1） broker 替订阅者吞，吞不下就丢 完全无感 丢，而且默认没有任何告警

实测时的画面很说明问题：压测工具对外发布跑到每秒一万三千多条，速率曲线平滑得像一条直线；同一时刻，订阅端每秒只收了不到三百条。发布侧完全不知道下游在挨饿。

这带来两个非常实际的推论：

  • 测 MQTT 段的吞吐，不能照搬 Kafka 的「阶梯加压看发布侧是否衰减」。发布侧永远不会衰减——你得使劲加压，然后看订阅端自己的接收速率在哪里封顶，那个平台才是真正的天花板。
  • MQTT 段必须自己埋丢包观测。Kafka 的积压是可见的（lag 是公开指标），MQTT 的丢弃是静默的。如果不主动比对「发布速率 vs 订阅速率」、不看 broker 侧的丢弃计数，过载时没有人会知道。

九、还有一层：慢订阅者会被直接掐断

如果只有「静默丢弃」，那至少还是一个可控的降级。但实际发生过一次更难查的现象：压测时吞吐怎么都上不去，订阅端的 CPU 反而越压越低，进程健康、探活全过，但就是收不满。

根因是 broker 的一条保护策略：为了防止单个慢消费者拖垮节点，当某个订阅连接的内部邮箱积压超过阈值（默认值很小，是为「海量小客户端」设计的），broker 会直接强制关闭这条连接。

于是慢订阅者进入一个恶性循环：积压 → 被掐断 → 重连 → 重新订阅 → 又积压 → 再被掐断。表现就是吞吐假封顶，而所有健康检查都是绿的。

把它调大之后，同一条链路的吞吐直接提升了一个量级，重连次数归零。这条经验很值得记：默认值是按「很多小客户端」调的，而我们的场景是「少数几个大吞吐订阅者」，方向正好相反。

与之配套的还有一条纪律：订阅者必须做到「重连后自动补订阅」。否则连接被掐断之后不会自己恢复，整个接入层会变成永久静默——数据不再进来，但没有任何一个指标会报警。这两件事是同一条故障链的两半，缺一半都不算修好。

十、重连风暴：最危险的是恢复的那一分钟

长连接还有一个只在「大规模恢复」时才出现的风险：所有设备同时重连。

平时设备掉线是零散的，重连也是零散的，broker 无感。但如果发生区域性网络抖动、或者 broker 集群重启，上万台设备会在同一时刻发现连接断了，然后同时开始重连。这一刻 broker 面对的不是数据洪峰，而是连接洪峰：TLS 握手要吃 CPU、认证要查一次身份、每个连接要分配内存和文件描述符。

结果是连锁的：握手打满 CPU → 部分连接超时 → 那些设备再重试 → 雪上加霜。一次「恢复」反而变成了比故障本身更严重的事件。

我们在两端都做了约束：

  • 设备侧：退避 + 抖动。重连间隔不能是固定的一秒，必须是指数退避加一个随机抖动——否则所有设备会像节拍器一样同步重试，永远撞在一起。
  • broker 侧：连接限速与认证缓存。允许每秒新建的连接数要有上限，把洪峰摊平成一段缓坡；认证结果要缓存，避免每来一个连接就打一次后端。

判断恢复是否健康，看的是重连速率而不是连接总数。连接总数最终一定会回到正常值，但如果重连速率长时间维持在高位，说明设备在反复掉线重连——那是最消耗资源、也最难察觉的状态。

这和上一篇文章里「补发要限速、要错峰」是同一类问题：集中爆发的资源争抢，永远比平均负载更危险。区别只是那次爆的是数据，这次爆的是连接。

十一、连接规模的运维面

MQTT 在别的场景里以连接密度见长——几十万设备直连，每台一条长连接。我们这个拓扑里没有撞上这堵墙（连接只有场站那么多），但只要把网关这一跳去掉、让设备直连，它立刻变成主要矛盾：每连接约占十几 KB 用户态内存，百万连接大致对应十几 GB，摊到多节点上才可算。

所以下面两个坑，在"设备直连"的形态下是必踩的；我们的形态里它们暂时不痛，但迟早会在另一处出现。

但有两个运维坑几乎每个项目都会踩：

  1. 文件描述符限制。默认的单进程 fd 上限往往只有一千，意味着 broker 在第一千个连接上就会崩——这是个非常常见的生产事故，必须显式调到百万级。
  2. 同机压测的假上限。压测客户端和 broker 在同一台机器时，每条连接都会占一个客户端临时端口，而系统默认的临时端口范围只有两万多个。连接数会卡在这个数上，看起来像是 broker 撑不住，其实是端口用完了。要真实验证连接密度，压测机必须分散。

十二、边界：什么时候不需要这一跳

  • 源已经在稳定内网。机房里的服务对着内网上游拉数，直接写 Kafka 就好，多插一跳 MQTT 没有收益。
  • 设备数量很少、允许丢。几十台设备、非关键数据，一个 HTTP 上报甚至定时批处理就够，没必要为一个不存在的规模上长连接。
  • 没有运维长连接的能力。broker 本身不难跑，难的是上面那堆默认值、重连风暴、连接数与端口这些运维细节。没有人盯着，它会以「静默」的方式坏掉——这比直接挂掉更危险。

这一篇讲的是「怎么把数据接进来」。下一站是 FEP：数据进来之后，它还是一个叫 P-3A-07 的原厂点号，平台并不知道它是哪台设备的哪个测点。点表翻译该放在边缘、放在平台，还是单独占一层——这个决定会牵连到另外三件事。
