FEP 前置——点表翻译该放在哪

IoT 高并发实时数据链路 · 第 6 篇

翻译不是一个函数，是一个边界。它决定了三件事：改一次模型要动多少台设备、认不出来的点怎么办、以及缓存失效的那一瞬间会发生什么。

把它放在哪里，本质上是在选「谁的变更半径最大」。放在边缘，半径是上万台设备；放在平台侧各消费者，半径是每一处消费代码。

说明：本文涉及的系统与规模做过脱敏处理，数字用于说明方法与量级关系，不一一对应某个具体项目。

一、数据进来了，但平台不认识它

上一篇讲完，数据已经越过弱网、进了平台的网络边界。但它现在长这样：设备 WTG-0231 发来一条报文，里面是 P-3A-07、P-3A-08、P-3B-01 三个原厂点号，值是 12.7、0、1543。

平台的世界完全是另一套坐标：它认识的是「设备 ID + 测点 ID + 数据类型 + 单位」。P-3A-07 到底是齿轮箱油温还是机舱温度？单位是摄氏度还是 0.1℃ 的整数？是模拟量还是开关量？这些信息在报文里没有，只在点表里。

顺便把报文的物理形态交代清楚，因为后面很多边界都跟它有关：报文是定长头 + 变长体。头部带设备标识、采集时间、序号和点数；体部是按点表顺序排列的「(原厂点号, 值, 质量位)」三元组。

解析这类报文，最容易出问题的不是翻译，而是边界：头部声明的点数与实际长度对不上、单点长度越界、尾包被截断。这几种情况只能整帧拒绝并计数，不能"尽力解析出半条"——半条报文比没有报文更危险，因为它会以合法数据的身份流进下游。

所以链路上必须有一步「翻译」：把原厂坐标映射到平台坐标。听起来像一个查表函数，但它的位置远比它的实现重要。

二、翻译的位置，本质是选谁的变更半径

有三个候选位置：

为什么 B 明显更优，原因不在性能，而在变更半径：

  • A（边缘）：模型一变，上万台设备都要更新点表。而现场设备「常年不升级」是常态——于是平台会慢慢不敢改模型，最终数据的定义被硬件冻结。
  • C（消费侧）：每个消费者各写一遍翻译，同一条数据在四条链路里可能有四种映射结果。出了问题无法判断谁对。
  • B（单独一层）：模型变更只改一处配置，两侧都不动。

顺带说，这也是为什么我们明确写下一条纪律：边缘只上原厂点号，不认平台身份。边缘不是不能做这个映射，而是「做了之后，平台就失去了改模型的能力」。

三、未映射的点：丢弃、计数、不猜

翻译层一定会遇到一种输入：报文里有个点号，点表里没有。

处理方式只有三种，而两种看起来更"友好"的做法都是错的：

做法看起来实际后果
透传（用原厂点号直接写下去） "至少数据没丢" 下游的存储 key、告警规则、查询索引全部出现两种命名体系——整个 key 空间被污染
猜（按名称相似度自动匹配） "能自动补上" 错映射比不映射更糟：数据进了错的测点，而且看起来完全正常
丢弃 + 计数 "数据丢了" 丢的是一条本就没有身份的报文；计数让它可见，运维能立刻知道该补点表

我们选第三种。它的关键是最后两个字：计数。丢弃本身不危险，静默丢弃才危险——「未映射点数」必须是一个被观测、被报警的指标，否则点表少了一条配置，你不会知道，直到某天业务方问「这个测点为什么没有数据」。

这条原则可以推广成一句话：系统可以拒绝数据，但不能假装没看见数据。

四、值闸：判完之后怎么办

第 3 篇讲过「清洗放边缘最便宜」，那里说的是无状态、逐点可判的清洗——非法值、坏质量码、超量程。而 FEP 这一层的校验不太一样：它要按平台配置判，比如这个测点的量程范围、这个设备该有的取值范围。这类校验依赖点表，所以放在翻译之后。

两种校验的分工是清楚的，但有一个问题两边都会遇到：判出来之后，是丢掉，还是标记？

「丢掉」是最容易想到的答案——既然不可信，不发就行了。它简单、省事，而且从「不让脏数据流下去」的角度看似乎无懈可击。但它会让下游失去一个重要区分：

「这个点没有数据」和「这个点有数据，但数据不可信」是两件完全不同的事。

前者可能是设备离线，后者可能是传感器故障。前者要补数，后者要派人去看传感器。一旦在闸门处丢掉，两者在下游眼里长得一模一样，处置方式自然也就会错。

所以值闸的输出不应该是「有」或「没有」，而应该是「值 + 它的可信度」：判出可疑之后保留并打上质量标记，让下游知道「这个点在坏质量状态，不要拿它做判断，但要把这个状态说出来」。

这里有个反例值得记下来：我们考虑过一个看起来更省事的替代方案——坏质量时沿用「上一帧的值」。它对变化率类规则是直接算错的：值没变，规则会得出「速率 = 0 ⇒ 已回落」，而坏质量根本不该判回落。用「看起来正常」的值去填补空缺，比让空缺露着更危险。

要把质量标记真正落地，得同时改三处：数据模型里加质量字段、判定规则里加一条「坏质量不判但重申」的分支、以及闸门本身从丢弃改成标记。三处不同步，就会出现「有些路认这个字段、有些路不认」的半成品状态——这类横跨三层的改动，要么一次做完，要么先别开始。

五、三级缓存：价值不在命中率，在失效瞬间

先算一下这笔账。整个平台的测点映射是百万量级的：一条映射要记原厂点号、平台测点 ID、数据类型、单位、量程，加起来一百多字节，百万条就是几百 MB。而 FEP 每秒要处理几万帧报文、每帧上百个点——每秒百万级的查表次数。

这个规模直接排除了两个方案：每帧查一次数据库（打爆连接池），或者全部走共享缓存（每秒百万次网络往返，Redis 也扛不住）。所以点表必须落在进程内内存里，而且每个实例都得持有全量——几百 MB 换每秒百万次零往返，这笔账非常划算。

问题随之而来：进程内缓存怎么在多实例之间保持一致。这就引出了三级结构：

  1. L1：进程内，最快，但每个实例各一份；
  2. L2：共享缓存（Redis），跨实例一致，但多一次网络往返；
  3. L3：回源，直接查权威存储。

看起来二级就够了，为什么还要第三级？答案藏在失效的顺序里：

写侧失效的顺序是「清理 → 广播 → 重建」。而广播清理 L1 的那一刻，L2 也是空的。

这个窗口非常短，但它真的会发生：一条报文在这个瞬间到达，L1 被清空了，去查 L2 也是空，于是它被判成「未映射」而丢弃——并且计入未映射计数，看起来像是一次正常的点表缺失。第三级回源就是用来堵这个窗口的：宁可多一次慢查询，也不要在这个瞬间丢数据。

有意思的是量级：实测 L1 命中率约 96.5%，而 L2 累计只命中了四百多次。也就是说，L2 几乎不承担正常流量，它存在的意义主要是「L1 被清空后别直接打数据库」。

这带来一个反直觉的结论：多级缓存的价值不在命中率，而在失效瞬间的正确性。如果只按命中率去评估，L2 和 L3 几乎都该被砍掉；但它们防的不是常态，是那个几千分之一秒的窗口。

六、一次点表变更，是怎么走完全集群的

「改一处配置」听起来很轻，但它要真正生效，得穿过所有正在跑的实例。这条路径值得写清楚，因为它是「翻译放 FEP」这个决定能不能兑现的关键。

完整的一条路径是：

  1. 改配置并升版本号。点表变更不是原地覆盖，而是产生一个新版本——这是回滚的前提。
  2. 广播失效。通知所有实例：L1 清空。此时共享缓存里的旧版本也一起清掉，避免实例从 L2 拿回旧数据。
  3. 各实例按需重建。下一个请求到达时，从回源重新加载，然后继续正常服务。
  4. 版本收敛。每个实例上报自己当前的版本号，全部等于新版本才算真正生效。

第三步到第四步之间，就是前面说的那个「窗口」。窗口里发生的事必须提前想好：如果这时来了一条只有新版本才认识的点号，它会被判成未映射——所以点表变更必须和「未映射计数」的监控一起看，否则变更期间的那点丢弃会完全隐形。

第四步是最容易被忽略的一步。很多系统只做到「广播成功」，就认为变更生效了；但广播是异步的，某个实例可能因为重启、网络抖动而没收到，它就会一直用旧点表工作。「发布了」和「生效了」不是一回事，只有版本号收敛才算生效。

版本号还顺带解决两件事：回滚（把版本改回去再广播一次，路径完全相同，不需要特殊的回滚流程）和灰度（先让一部分实例升版本，观察一段时间再全量）。这两件事在「原地改配置」的做法下都很难做。

七、去重为什么放在翻译之前

FEP 里的处理顺序是：先判重，再翻译，最后攒批。这个顺序不是随手排的。

判重需要的信息其实很少：这台设备、这个序号，我是不是已经处理过了。它不需要知道这个点叫什么。而设备身份从 MQTT 的 topic 里就能拿到，序号在报文头里，两者都不依赖点表。

所以把去重放在最前面，有两个直接好处：

  • 省掉无用的查表。重复报文会被直接丢掉，不会浪费一次点表查询、一次值校验、一次序列化。
  • 让去重语义更稳定。即使点表配置错了、缓存失效了，去重这一层仍然按「设备 + 序号」正常工作——它不依赖任何容易被改坏的东西。

这也和第 4 篇那条结论咬合：去重的判据是「同一设备的有序前缀」，而设备的边界在 MQTT 这一层就已经确定了。翻译、清洗、判定都建立在这个边界之内，反过来则不成立。

八、两个「批量」不是一回事

这里有个容易混淆的地方值得先讲清楚：链路上其实存在两种完全不同的「批量」，一个是语义层的，一个是性能层的。

第一种：一条报文里装什么，是在边缘就定好的

边缘网关上送的一条原始报文，不是「一个测点一条」，而是「一台设备、一次采集周期、它的全部测点」——报文头带设备标识与序号，报文体是按顺序排列的一串点位（原厂点号 + 值 + 质量位）。

这个结构是边缘侧的报文定义决定的，不是在平台侧拼出来的。它直接决定了两个量纲的关系：

点率 ÷ 报文率 = 一条报文里的测点数

一台设备上百个测点，这个比值就是上百倍。所以「每秒多少点」和「每秒多少条」天生差两个数量级——这不是谁攒出来的，是报文结构本身决定的。容量估算里只要把这个系数搞错，后面所有结论都会偏。

第二种：FEP 的攒批，是发送侧的优化

在上面那个报文结构之上，FEP 还有一件可做的事：把多条报文合并成一次下游写入。它解决的不是「一条报文里有几个点」，而是「一次写多少条报文」——摊薄序列化、网络往返与批量提交的成本。

两个上限取先到者：

  • 按条数攒：累计到一定量就发一次；
  • 按时间攒：最多等一个固定时间（比如一秒），到点就发，不管攒够没有。

只按条数攒，低频设备可能很久都凑不够一批；只按时间攒，高峰期的批又太小。两个一起用，才能在「摊薄」和「不滞留」之间取平衡。代价是一段确定的延迟——对秒级时效可以接受，但如果有人要求毫秒级可见，这正是第一个要重新权衡的地方。

还有一条硬约束：攒批不能跨设备。下游要按设备做分区键保序，如果一批里混了多台设备的数据，这一批就没法用一个键路由。所以攒批的边界天然是设备。

把两者放在一起看：第一种批量决定了「最小传输单位」的语义，第二种批量只是把这个单位再合并发送。前者是设计，后者是优化——优化可以关掉，语义不能改。

九、边界：什么时候翻译可以合并进边缘

这套「翻译单独一层」的设计不是无条件的。它在下面这些情况下会显得过重：

  • 单客户、模型几乎不变。如果点表三年没动过，且设备升级通道顺畅，把翻译下沉到边缘可以省掉一个组件。
  • 设备数量很少。几十台设备的规模，批量推一次配置是分钟级的事，变更半径不构成问题。
  • 没有多租户概念。一旦要按租户隔离坐标体系，独立一层几乎是必然的。

判断标准还是那条：你的变更半径有多大，决定了这一层该不该独立。模型会频繁演进、设备又推不动的地方，翻译就必须是一个独立的、能单独发版的东西。
