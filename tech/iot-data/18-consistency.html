端到端一致性——没有事务，靠什么收敛

IoT 高并发实时数据链路 · 第 18 篇

这条链上没有一处跨系统的分布式事务。一致性不是靠某个机制"保证"出来的，而是靠三个动作叠出来的：每一步幂等、每一步可重放、每一段留账。

而更要紧的是另一半：每一处都明确放弃了点什么。能说清放弃了什么，比声称"最终一致"有用得多。

说明：本文涉及的系统与规模做过脱敏处理，数字用于说明方法与量级关系，不一一对应某个具体项目。

这一篇是横向收束，不复述机制。前面各篇已经就地讲透的东西——时间锚怎么推、outbox 的两种形态、去重与攒批的区别、分区键为什么选设备——这里只引用结论，不再展开推导。

一、先把问题问准："一致"指的是哪句话

"端到端一致"这个说法本身是模糊的。它听起来像一个可以整体达成的状态，实际上不是——一致性永远是针对某一句具体断言说的。脱离了断言去谈"一致"，讨论很快就会滑向 CAP 之类的抽象，然后什么也决定不了。

所以先落到地上。这条链跑起来之后，真正会有人来问的，其实只有四句话：

有人会问的背后的真问题出错时的样子
「大屏上明明有这条告警，点进去历史里查不到」 跨存储的可见性撕裂 两个页面同时打开，答案不一样
「短信我收到了，系统里查不到这条告警」 通知与记录不同步 外部证据比内部记录更早
「同一条告警，一晚上通知了我三次」 重复 用户直接失去信任
「上个月某段时间的数据少了一块」 静默丢失 一周后才被发现，且无法补

这四句话有一个共同点：它们都是可以判定的。"一致"如果不可判定，就没法验收；而这四句每一句都能写成一个查询、一个指标，或者一次演练。

于是工程上能做到的事也就清楚了：不是"所有地方随时一致"，而是"这四句话都有明确答案"——要么设计上不会发生，要么发生了能被发现，要么发现了能补。

没有全局的「一致」，只有一条一条能够被验证的断言。

这一点定下来之后，后面所有讨论都不必再抽象：任何一处设计，我们只问它守住了哪几句、放弃了哪几句。

二、一张总表：每一处保证什么、放弃什么、怎么观测

把整条链从头到尾走一遍，每一处都填三样东西。这张表是这篇的骨干——它的每一行都是一个独立的小契约，而端到端的一致性，就是这些小契约首尾相接的结果。

位置保证什么放弃什么怎么观测
边缘补发 按设备序号有序；进程重启后，未确认的那一段还在盘上 缓冲窗口之外的数据——窗口是有界的，满了就得丢 缓冲水位 + 最旧未发序号距今时长
MQTT 投递 逐跳确认：上一跳收到才算发出 订阅者慢时直接掐断；缺席期间的消息全丢，且客户端不知道 重连次数 + 掐断计数
接入前置去重 进程内的序号水位挡住重投 实例漂移或重启后水位丢失，窗口内可能重放 去重命中数 + 无序号报文计数
消息层 分区内严格有序；留存期内不丢；可回放 跨分区没有任何顺序保证 每分区 lag + 留存到期丢弃量
历史写入 至少一次；重复写由时间戳覆盖收敛 积压超过留存期后，消息被过期删除 丢弃计数 + 批重试次数
实时快照 每台设备"后写赢"，且靠时间戳防回跳 位移不提交会导致重投；短时内同一批可能写两次 快照年龄（最新数据距当下）
告警判定 → 业务 at-least-once；同一事件由唯一键收敛成一条 同一事件会被处理两次，第二次撞键后放弃 唯一键冲突计数
告警记录 + 审计流水 同一个本地事务：要么都成、要么都不成 无——这一跳是全链唯一真正原子的地方 事务提交数 vs 事件消费数
决议 → 通知任务 任务不丢；卡住的能被扫描捞起继续推进 产出可能重复（由台账的唯一键挡住） 卡在中间态的任务数
站内推送 广播范围内，在线连接必达 断连期间不补；中继瞬断时，那台机器上的连接会漏 订阅被拒计数 + 重连后快照拉取次数
站外投递 至多一次；账上一定有记录 可能漏一条——但漏了可查、可人工补 提交量 − 回执量
审计流水落表 纯追加；分区内唯一 跨分区边界极小概率重复 重复组数探针

这张表最好像读一份合同一样从左往右读：

  • 「保证什么」是设计——它由某个具体机制提供，比如确认、唯一键、本地事务；
  • 「放弃什么」是代价——没有一行是"全都保证"的，凡是声称全保证的，多半是没想清楚；
  • 「怎么观测」是承认——承认这条代价真实存在，所以留了一个数盯着它。

三列里最容易空着的是第三列。而它恰恰最重要，因为有一个判据可以一眼用上：

哪一行的「观测」是空的，那一行的「保证」就不可信——
因为它坏了，没有任何人知道。

按这个判据回头扫一遍，你会发现表里有几行的观测是明显的，有几行是勉强的。差的那几行，就是你系统里真正的薄弱处——不是设计错了，而是设计对了但没人盯着。

还有一点值得指出：这十二行里只有第八行（告警记录 + 审计流水）是真正原子的，其余十一行都是"最终收敛"。这不是偷懒——是因为它两边的东西在同一个库里，本地事务成本几乎为零；而一旦跨出去，成本就从"一次提交"变成"一整套补偿机制"。

三、三个可复用的模式

把上面十二行抽象掉具体实现，剩下的东西只有三个。它们不是这条链独有的，凡是"没有分布式事务、但又要收敛"的系统，用的都是这三样。

模式一：本地事实表 + 追认

第一个模式的形状是：先把事实落在自己库里，再对外承诺；跨系统的两段各自有账，中间用消息连接，而不是用事务连接。

它成立的前提只有一句判断：

能不能放进同一个本地事务？能，就别拆。

这句话值得反复用，因为它反过来纠正了一个很常见的惯性——"为了架构统一，所有跨组件写都异步"。这个思路在有分布式事务能力的系统里也许成立，但在这条链上，它把一件本来免费的事（同库两条写，一次提交）变成了要额外付费的事（重试、去重、对账、补偿）。

真正需要拆的只有一种情况：两件事实分属不同的存储，而它们必须都发生。这时才引入"本地事实表 + 追认"——先在自己这边把事实写死（这是唯一需要原子的一步），再异步地把这个事实推给对面；推失败了就重推，因为本地有账，重推是安全的。

所以这个模式真正的价值不是"异步解耦"，而是把"跨系统原子"这个做不到的事，换成了"本地原子 + 可重推"这个做得到的事。两者的差别不在理论，在于前者需要一个我们根本没有的东西。

模式二：幂等键怎么选

第二个模式回答"重推为什么安全"。答案当然是幂等键，但难的是怎么选——选错了，幂等就是假的。

我们用的三条判据，按重要性排序：

判据为什么违反它会怎样
写入方手里就有，不需要先查 如果键要先查库才能构造，就等于把一次全局查询塞进了写入路径 幂等机制本身成了瓶颈，或者退化成"查—不存在—写"的竞态
同一业务事件必然算出同一个值 这是幂等的前提：重放必须落在同一个键上 重投变成新记录，等于没有幂等
粒度与保留期匹配 键的唯一性只在保留期内可验证，过期数据删了就没法拦 跨窗口的重放拦不住，但它已经不构成业务问题

按这三条去看，几种常见的选法是错的：

  • UUID——每次生成都不同，重放必然产生新键。它防的是"不同事件撞车"，不是"同一事件重复"；
  • 自增主键——由存储生成，重放时自然也不同，同样拦不住；
  • 直接用"当前时间"——重投时时间已经变了，键就漂了。

反过来，"业务标识 + 一个时间锚"是有效的，因为它在写入方手里就能算出来，而且同一个事件重投时算出来一定一样。前面几篇里那三种锚——分钟桶、代际、承诺时刻——选择的依据其实只有一条：这个业务事件的"同一性"由什么决定。逐条事件由分钟决定，聚合由窗口决定，升级由承诺那一刻决定。选锚不是技巧问题，是先把"什么算同一件事"想清楚。

还有一个容易忽略的维度：幂等键要落在有唯一约束的地方。写在代码里的 if-else 去重，在多副本下等于没有——两台机器同时判断"不存在"，然后同时写入。真正的幂等必须靠存储层的唯一索引兜住。

模式三：对账兜底

前两个模式解决"设计上不该出错"。第三个模式承认一件事：设计上不该出错，不等于不会出错。所以还需要一个定期去数一数的动作。

对账最容易被误解成"补数据"。它真正的职责是发现哪一段承诺没有兑现——补是后面的事，先得发现。

一个可用的对账，必须回答三个问题：

  1. 比对哪两个集合？左边必须是"我们承诺要做的"，右边是"实际做成的"。比如左边是提交出去的投递任务，右边是回来的回执——缺的那部分就是缺口。
  2. 允许多长时滞？没有时滞定义的对账是没法定成败的：刚写进去的还没落盘，你一去数就全是缺口。时滞必须大于正常路径的最长耗时。
  3. 发现了谁来处置？没有处置动作的对账，只是一个报表——数会一直涨，没人知道该干什么。

另外有一条克制原则：探针只覆盖最可能出问题的那一段。因为对账本身是有成本的——它是聚合查询，扫全表就成了"为了观测问题，制造一个新的负载问题"。重复和缺口绝大多数是新近产生的，老数据即使发现了也无从补救。所以扫最近几天、在低峰期跑、结果落成一个 gauge，是更合理的形态。

三个模式合起来看，其实是三种不同的"治":

模式治的是成本
本地事实表跨系统写不能原子多一张表、多一个扫描
幂等键重推会重复键的设计成本 + 索引体积
对账以上两者都可能被绕过持续的查询负载 + 人的处置流程

三者是递进关系：没有前两个，对账会天天报警；没有第三个，前两个错了你不知道。

四、诚实清单：哪些地方明确放弃了

前面讲的全是"保证了什么"。但一套设计可信不可信，往往看它敢不敢说"哪里放弃了"。下面是这条链上的诚实清单：

位置放弃了什么最坏情况谁兜底
站外投递 不重复 漏一条短信或电话 台账可查 + 人工补发
边缘补发 超出缓冲窗口的数据 长时间断网后，早期数据永久丢失 补发尖峰的丢弃计数会留下痕迹
历史写入 缓冲满后的新数据 积压超留存被删，静默 丢弃计数 + 对账缺口
站内推送 断连期间的消息 那段时间的告警在页面上没出现过 重连后重新拉快照
审计流水 跨分区边界的严格唯一 极小概率多出一行 重复组数探针
实时 vs 历史 两者的瞬时一致 同一时刻两个页面数字不同 快照年龄指标 + 页面标注数据时刻
通知 vs 记录 先后顺序 短信可能比系统里的记录早几秒 台账上有时间戳，能解释

这七行有一个共同的处置方式：都不靠"更努力地保证"来解决，而是靠"留痕 + 可解释 + 可补"。

这里有一句话想单独说：这份清单如果写不出来，就说明"最终一致"只是一个口号。因为写不出来通常意味着两种状态之一——要么根本没想过边界在哪，要么想过但不愿意承认。两种都会在出问题时变成"这不应该是我们的问题"。

而写出来之后，还有一个额外的好处：它能直接回答用户的问题。当有人说"这两个页面数字不一样"，你不必现场排查——你能直接告诉他"你看的是实时视图还是历史视图，两者允许差几秒"。这不是推诿，这是把系统的性质讲清楚。

五、强求强一致，要付什么

到这里一定会有一个反问：既然放弃了这么多，为什么不去要强一致？

这个问题值得认真回答，因为"我们选择最终一致"如果没有另一半，听起来就像在给自己找理由。所以我们挑三个最典型的诉求，各算一笔账。

诉求一：让告警记录、审计流水、历史在同一笔事务里

这三样东西分属不同存储——关系库、时序库。要做到"要么都成"，就得引入跨存储的两阶段提交。

代价不只是"慢一点"：

  • 事务持有时长取决于最慢的参与者。一次提交要等所有参与者投票，而其中一个是按批写入的时序库——它的响应时间本来就比关系库长一个量级；
  • 参与者不可用时会悬挂。协调者挂在中途，参与者持有锁等指令，等到超时；这段时间里那些行谁也动不了；
  • 吞吐掉一个量级，因为原本可以并行的写入被强制同步在一个提交点上。

而收益是什么？避免了"告警记录有了、历史还没写"。可这个问题本来就可以用更便宜的方式解决：告警记录里带上它对应的时间段与设备，出现不一致时能定位、能补写。用一次补偿换掉一整套 2PC，这笔账在任何量级上都是划算的。

诉求二：让站外投递"不重不漏"

这个诉求做不到，原因不在我们这一侧——第三方渠道没有幂等键。你没法对运营商说"刚才那条别重复发"。

所以在"可能重复"和"可能漏"之间，必须选一个。我们选了可能漏，因为它可查、可补；而重复不可撤回——消息到了人手机上就是到了。

这里的关键认识是：强一致的前提是"所有参与者都能配合"。外部系统不配合，你要么接受弱一点，要么自建一条端到端可信的通路（那是另一个量级的工程）。

诉求三：让四路消费严格同步

历史、实时、告警、派生是四个独立消费组。让它们"同一时刻看到同一批数据"，等于把它们合并成一个消费组。

代价是三重的：一路慢，全网慢（失去了隔离）；回放能力消失（合并后位点只有一个，回放历史就会同时污染实时视图）；扩容受限（并发上限从四个分区集合变成一个）。

而收益只是"四个页面同时刷新时数字一致"——但这件事本来就该由界面解决：页面标注数据时刻，让用户知道自己在看哪一刻。用界面上的一个时间戳，换掉后端的三个能力，不划算。

一把尺子

三个诉求算下来，可以归纳成一句话：

强一致的成本，本质是把并发换成等待。
而这条链的并发单位，是每秒百万级的测点。

所以判断"要不要强一致"的方法其实很简单：先问这件事的并发量级。如果是每天几十次的操作（比如配置变更、权限调整），上强一致毫无问题；如果是每秒百万次的数据路径，强一致就等于自缚手脚。

这条链上的边界因此很清楚：低频的管理动作可以强一致，高频的数据路径只能最终一致。这也解释了为什么第八行（告警记录 + 审计流水）可以是原子的——它俩在同一库里，且频率是"事件级"，不是"测点级"。

六、不是"多久之后一致"，而是"多久之后可判定"

这一节是这篇唯一一个新提法，因为它纠正了一个很普遍的模糊。

"最终一致"里的"最终"，通常是没定义的。问"多久之后一致"，得到的回答往往是"很快就好了"——这不是承诺，这是语气。

更有用的问法是：这件事，什么时候可以被判定为出问题了？

因为一个数据在它生命的每个阶段，"正常"的标准不同。刚产生的那一秒还没落库，是正常的；过了五分钟还没落库，就是缺陷；过了一天对账差量还是非零，就是事故。这三种"不正常"，性质完全不同，处理方式也完全不同。

所以我们把它拆成三个窗口：

窗口量级窗口内不算问题，因为过了窗口说明
重试窗口 秒到分钟 还在重投、还在重连、还在攒批 正常路径已经走不通了，该报警
对账窗口 小时到天 批量任务还没跑完，回执还没齐 有一笔承诺确实没兑现，该定性
归档窗口 月 数据还在热区，随时可查可补 证据即将消失，再查就没机会了

这三个窗口带来两个很实用的推论。

第一，报警阈值必须按窗口设，不能按感觉设。很多"误报"其实不是误报，是阈值设在了重试窗口里面——系统还在正常重试，你就开始报警了。反过来"漏报"通常是阈值设在了对账窗口外面，等你发现时数据已经补不回来了。

第二，这三个窗口各自属于不同的人。重试窗口是值班的（分钟级，要立刻动）；对账窗口是数仓或运维的（按天看）；归档窗口是合规的（按月）。如果三个人盯着同一个数，就会互相以为对方在看。

把"最终一致"翻译成"多久之后可判定"，最大的好处是它变得可以验收：每一个窗口都能写成一条规则，写不成规则的就说明还没想清楚。

七、怎么证明它真的收敛了

前面所有设计都是"应该能收敛"。最后一个问题：你怎么知道它真的收敛了？

答案只有两样东西——对账的结果和演练的结果。前者是平时的证据，后者是故障时的证据。

看差量，不看比率

这条链上真正有意义的指标，几乎都长成"两个数相减"的样子，而不是"一个比值"：

指标形态为什么比率不行
提交量 − 回执量差成功率的分母是"提交了多少"，漏发根本进不了分母
消费 lag差吞吐曲线漂亮的时候，lag 可能正在稳步上涨
丢弃计数计数丢弃不影响任何成功率，它是纯损失
重复组数计数重复不报错，只会让"历史"这句话变得不可信

这些数有一个共同特征：它们不在"成功/失败"这个维度上。一个系统可以成功率 100%、健康检查全绿，同时持续丢数据——因为丢的那部分从来没有进入过任何分母。

所以这条链上的每一层都要求一个"损失计数"。这个要求在第七篇讲背压时提过一次，这里补上它的用途：它是唯一能穿透传导链的东西。下游慢了，上游看到的是"消费正常"；只有那个丢弃计数，会在上游完全不感知的情况下，把真相留在原地。

断链演练：证明"坏了能看见"

监控能告诉你"现在像不像正常"。但它证明不了另一件事：真坏的时候，我会不会知道。

所以还需要一个动作——在测试环境里，故意把某一段停掉，然后看哪个数动了：

  1. 停掉历史写入 → 应该看到丢弃计数上涨、对账缺口出现；
  2. 停掉一个消费副本 → 应该看到 lag 上升、再平衡发生；
  3. 停掉回执接收 → 应该看到"提交 − 回执"这个差单调上升；
  4. 掐断一个 MQTT 连接 → 应该看到重连计数跳一次、快照重新拉取一次。

这四步里，只要有一步"什么数都没动"，那就比故障本身更严重——因为这意味着这类故障在线上发生时，你同样什么都不会知道。演练的价值不在于验证系统能不能扛，而在于验证观测能不能看见。

这也是这一篇和最后一篇的接口：有一类失败，进程健康、接口 200、日志无错，但数据是错的。前面十二行的"观测"列，防的就是这一类。

八、边界：什么时候不必这么讲究

  • 单机单库。所有写入在同一个数据库里，本地事务就够了——上面这一整套（outbox、幂等键、对账）全部可以省掉。这也是为什么"先别拆"往往是对的。
  • 数据可丢。如果丢几条不影响任何业务判断，那么背压、补发、对账的价值都很低。
  • 只有一路消费。多路才需要谈"两路之间的不一致"，单路时那些讨论都是空的。
  • 量小到人工可核。一天几十条记录，人对一遍就能发现缺口，比建一套探针便宜。但要写下这个前提——它会在规模上去之后失效。

还有一个反向的边界值得说：不要为了"看起来严谨"而给低频路径也上最终一致。前面说过，低频的管理动作（配置、权限、流程）完全可以强一致，而且更简单。把一条每天十次的路径做成异步 + 幂等 + 对账，是把简单问题复杂化——而这在"统一架构"的名义下非常常见。
